# caracole on Android, in Kotlin

A plan for a phone app that keeps a library of its own and works with the computer off. It searches, looks songs up,
keeps songbooks and plays sheets. It syncs with the computer's caracole both ways, and the owner chooses a side
wherever the two differ. Nothing in it needs Termux or Python on the phone.

Status: a plan, not built. The research behind it, with sources, is
[superpowers/specs/2026-11-02-android-native-port-feasibility.md](superpowers/specs/2026-11-02-android-native-port-feasibility.md).
The sync protocol it builds on is designed in
[superpowers/specs/2026-10-31-phone-server-sync-design.md](superpowers/specs/2026-10-31-phone-server-sync-design.md)
and is built on the computer's side.

## In short

- **Feasible.** Every feature asked for can be written in Kotlin. None of them needs a native library beyond SQLite.
- **Most of what you see is already JavaScript, and is reused as it is.** The sheet viewer, the library page and the
  songbooks are about 15,000 lines of JavaScript, CSS and HTML. They include scrolling, transposition, the guitar and
  harmonica overlays and sound. A WebView runs them unchanged, as today's Android app already does for its offline
  copy.
- **What gets ported is what feeds those pages:** the database, search, lookups on the sites, indexing, sync,
  songbooks, and each sheet's data (music theory, chord shapes, harps, pinyin). That is about 28,000 lines of
  caracole's Python code, out of 41,000. Kotlin of the same logic is about as long.
- **The hardest part is not the sites or sync.** It is making the phone agree with the computer to the byte, on
  identity keys, sync digests and each sheet's music theory. A shared test corpus, generated by the Python suite and
  checked by the Kotlin one, holds the two together.
- **What stays on the computer:** the nightly run, building the site indexes, ChordPro's PDFs, auto-chords and
  YouTube.
- **The first useful milestone is small.** The phone searches the indexes with the computer off, and syncs songs
  both ways. Lookups and the page builder come after.

## What exists today

- **caracole** is a Python program. A NixOS service runs it every night to build a private library for the songs in
  `wanted.txt`: chord sheets (Ultimate Guitar, LaCuerda), lyrics (LRCLIB, Megalobiz, AZLyrics), PDFs (ChordPro),
  Guitar Pro files (gtptabs.com), harmonica tabs (harptabs.com), game-music tabs (gametabs.net) and MuseScore
  links. It keeps local indexes of those sites, so a search sends no request.
- **`caracole serve`** is its web interface on the LAN. It runs the library page (search, cards, songbooks,
  requests) and the sheet viewer. The pages are static HTML and JavaScript. They talk only to caracole serve, which
  runs every change as a queued `caracole` command.
- **The Android app** ([android/](../android/README.md), about 3,700 lines of Kotlin with its tests) is a read-only,
  offline copy of the computer's library. It downloads what `GET /api/offline` lists and shows it in a WebView, with
  pinch-to-resize text. It can't search the sites, add a song or change anything.
- **Sync between two caracoles** works on the computer's side today (`caracole peer diff`, `sync`, `pull`). It cuts
  a library into units: each song, each removed song, each songbook, and a few per-artist and per-tab settings. Each
  unit has a digest, and two libraries are compared three ways against the last state they agreed on. A unit
  changed on one side is that side's. A unit changed on both sides is a conflict for the owner to settle.

## The goal

1. On the computer, look up 20 songs and change the chords of some of them.
2. On the phone, sync. The 20 songs arrive with their changes.
3. With the computer off, the phone searches for new songs, lyrics and Guitar Pro tabs, and adds them.
4. Later, sync again. Each side has done things the other hasn't. The phone lists the differences, the owner picks
   a side for each one, and both end up with what was chosen.

## How the app is built

```
┌───────────────────────────── the app ─────────────────────────────┐
│ WebView: caracole's own pages, unchanged JavaScript               │
│   library page · sheet viewer · songbooks · harmonica tabs · sync │
│                │ HTTP, 127.0.0.1 only                             │
│ Local server (Kotlin): caracole serve's routes                    │
│                │                                                  │
│ Kotlin core: search · lookups · indexing · sync · songbooks ·     │
│              each sheet's data (theory, shapes, harps, pinyin)    │
│                │                                                  │
│ Bundled SQLite with FTS5, caracole's own schema · the files       │
└───────────────┬──────────────────────────────────┬────────────────┘
                │ HTTPS, polite                     │ HTTP, LAN or tailnet
      UG, LRCLIB, LaCuerda, …              the computer's caracole serve
```

- **One Kotlin core with no Android dependency**, tested on the JVM as `android/mirror` is today.
- **caracole's own SQLite schema**, the same tables and the same migrations. The schema's SQL is copied, not
  rewritten. An index exported on the computer is then an SQLite file the phone merges with plain SQL.
- **SQLite is bundled, not Android's own.** caracole's search needs FTS5: a trigram table (SQLite 3.34 or later),
  two `unicode61` tables and `fts5vocab`. Android's SQLite doesn't document FTS5, and reports say it lacks it. The
  candidates are androidx's `sqlite-bundled` (its docs don't say whether FTS5 is in, so check with
  `PRAGMA compile_options` on a phone) or sqlite.org's Android bindings built with `-DSQLITE_ENABLE_FTS5`, which
  they document.
- **A local HTTP server on 127.0.0.1** (Ktor's CIO engine is a candidate) answers the pages as caracole serve does.
  WebView request interception can't do it alone, because an intercepted request comes without its body, and the
  pages post forms. caracole serve has 52 routes. The features below need about 40 of them: all but YouTube's five,
  Export PDF, the offline copy's two and, at first, the Guitar Pro page's two.
- **Jobs** become coroutines on one queue. caracole serve runs each change as a child process and the pages poll
  `/jobs.json`. The pages keep polling, and the app answers. One process owns the database, so caracole's file lock
  and its handoffs to lookups become a mutex.
- **Security on the phone needs one decision.** On the computer, whoever can reach caracole serve may use it, by the
  owner's choice: no sign-in, no cookie, no secret. On a phone, any installed app can connect to a port on
  127.0.0.1. The proposal is a random secret per launch, which the app sets as a cookie in the WebView and the server
  requires on every request. The other rules come along unchanged: the host check, the form token, the cross-origin
  checks and each page's Content-Security-Policy.

## Feature by feature

Sizes are lines of Python code to port, without docstrings, comments or blank lines (radon's SLOC).

|---|---|---|---|
| 1. Searching the indexes | 2,200 | medium | FTS5 in the bundled SQLite; rapidfuzz's scores; Chinese as pinyin |
| 2. Looking a song up on the sites | 6,400, plus 1,400 of politeness | large | breadth: seven sites, each with its own parser and rules |
| 3. Indexing | 2,000 (import alone: a few hundred) | small to medium | none, if the computer builds the indexes |
| 4. Sync | 800, plus a new push | medium | the same digests and keys in both languages |
| 5. Songbooks | 1,100 | small to medium | the music theory, which they share with sheets |
| 6. Sheets and what they do | 6,100 | extra large | harmonica-tab reading, and agreeing with Python exactly |
| The local server and the library page's data | 4,600 + 1,100 | medium | the security rules, the job queue |

### 1. Searching the indexes

What it is: the search box on the library page. It finds your songs and the songs on every indexed site (UG,
LaCuerda, harptabs.com, gametabs.net, gtptabs.com, MuseScore), with "Did you mean" suggestions and progression
search. It reads SQLite alone and sends no request.

What the port takes:

- **FTS5** in the bundled SQLite (above).
- **rapidfuzz's scores, exactly.** caracole uses `fuzz.ratio` (36 calls), `partial_ratio`,
  `partial_ratio_alignment`, `token_sort_ratio`, `process.extract` and the OSA edit distance. Its thresholds were
  tuned on rapidfuzz's scores. A port of these few functions (Indel and OSA distances, and the partial-ratio window
  rules) is a few hundred lines. A fuzzywuzzy port would score differently.
- **Chinese compared as pinyin.** caracole reads pinyin with pypinyin (MIT). No Kotlin library matches it: pinyin4j
  and TinyPinyin read one character at a time, so a character with two readings comes out differently. pypinyin
  itself is small: forward maximum matching over a 2.5 MB phrase dictionary and a 0.8 MB character dictionary. Port
  the algorithm and ship the dictionaries as assets, and the results are exact.
- **Names read from free text** (song_names.py: "Artist - Title", a video's title and channel), and the key folding
  of normalize.py.

### 2. Looking a song up on the sites

What it is: `caracole get`, one song looked up now. It matches the song against UG's index, fetches the sheet, then
lyrics, LaCuerda, the Guitar Pro file, the harmonica tab and the game tab, each site in turn.

What the port takes:

- httpx becomes OkHttp, selectolax becomes jsoup, and Python's JSON becomes kotlinx.serialization. Every site is
  HTML or JSON over HTTP, so nothing needs a browser or a native library.
- **The politeness rules come whole, each with its tests:**
  - robots.txt honoured;
  - the lookup pace, 0.5–1.5 s between requests;
  - six requests to a site for one song, and 60 an hour for all lookups together;
  - one request at a time;
  - a block (403, 429, a challenge) as a cooldown with no retry;
  - errors never misses: a block or a parse error never marks a song not found;
  - every 200 and 404 cached.

  Each caracole counts its own budgets, and a cooldown one side met moves to the other at a sync.
- The cost is breadth, not difficulty. Do UG and lyrics first, then the other sites one at a time.

### 3. Indexing

What it is: caracole's local copies of each site's catalogue (sitemaps, artist listings, artist pages).

Building them on the phone would work but is the wrong job for it. UG's sitemaps are about 40 requests (some ten
minutes at the bulk pace, 70 MB downloaded, about 1 GB of XML parsed). They make 1.4 million rows and a database of
about 400 MB. The other sites take far longer: harptabs.com's 10,428 artist pages, at 10–20 s apart, are a day and a
half of requests on their own. Building on both sides would also double what the sites see.

So:

- **Import the computer's index.** `caracole index export` already writes one SQLite file, and its merge rules are SQL
  over an attached database: a small port.
- **Then carry it in sync.** A new `GET /api/peer/index` streams the export, and each side merges the other's. The
  artist pages the phone reads during its own lookups then reach the computer too.
- The phone refreshes nothing in bulk. Its lookups read the odd artist page, as they do today.

### 4. Sync

What it is: the protocol caracole already speaks (HTTP and JSON), plus a screen to choose sides.

What the port takes:

- **Digests that come out the same in both languages.** A unit's digest is the SHA-256 of Python's
  `json.dumps(sort_keys=True, separators=(",", ":"), ensure_ascii=False)`. Kotlin has to reproduce it byte for byte:
  keys sorted by code point (Kotlin compares strings by UTF-16 unit, which differs past U+FFFF), and Python's
  escapes. No unit holds a float today, and it should stay that way. Write the canonical form down as a spec with
  test vectors.
- **Identity keys that agree to the character.** Sync names a song `song/<identity key>`. The keys use caracole's
  own folding and its own Traditional-to-Simplified table (data to copy), and Unicode's NFKD, whose tables can differ
  between Python's Unicode version and the phone's for recent characters. Test vectors catch it.
- **One change on the computer's side first.** A version's raw record and a song's lyrics are hashed as the text
  stored. The same tab fetched by both sides, serialized by two languages, would then look changed on both, a
  conflict with no real difference. Hash them canonicalized instead, with a bump of the sync format so the two
  sides never compare across it.
- **The phone starts every sync.** Today each side pulls, so the computer would have to reach the phone's server.
  Instead the phone pulls what it takes, then pushes what the computer takes to a new `POST /peer/push`, with the
  form token as every write. The phone then serves nothing to the network.
- **The Sync page**, still to build on the computer too: the peer's address, the differences, a side for each, and
  Sync. Built as a tab of the library page in JavaScript, it serves both sides.
- **Rendered pages.** A sync of units carries no rendered page: each side renders what it takes. Until the phone
  has its page builder (feature 6), the app's existing mirror (`GET /api/offline`) brings the computer's rendered
  pages for the computer's songs. The mirror has to change for that: today it swaps in the computer's whole library,
  and here it keeps the phone's own songs beside it.

### 5. Songbooks

What it is: set lists, their order, and each song's setting (key, mode, capo, instrument), with a songbook's page
in the viewer.

What the port takes:

- The set lists and settings: small to medium. Keeping the key a song sounds in when the capo or the instrument
  changes needs the music theory of feature 6.
- The phone can keep songbooks and per-song settings in SQLite rather than in hand-edited TOML files, since sync
  moves units, not files.
- A songbook's page is the viewer's, reused. Its PDF is ChordPro's (see below).

### 6. Sheets and what they do

What it is: the sheet viewer. It scrolls, transposes, sets capo and mode, has the guitar and harmonica overlays, the
Harmony panel, strumming, other instruments (ukulele, piano, harmonica, flute, recorder), pinyin over the words, and
Simplified or Traditional characters.

All of that is JavaScript and is reused unchanged. The viewer computes no music theory itself: it looks every answer
up in tables the page carries. What Kotlin must build is each page's data:

| Part | Python | In Kotlin |
|---|---|---|
| Reading a UG or LaCuerda sheet (chordpro.py, viewer/sheet.py) | 440 | parsing, mechanical |
| Theory, keys, versions (theory.py, keys.py, version.py) | 1,210 | pure logic, mechanical |
| Harmony and its tables, progressions (harmony.py, harmony_tables.py, progressions.py) | 1,140 | pure logic; the catalogue of progressions is data |
| Chord shapes (voicings.py, instruments.py) | 360 | the voicing JSON files (84,000 lines) as assets; the piano's computed |
| The harmonica and the winds (harp.py, harpfit.py, winds.py) | 590 | pure logic |
| Harmonica tabs read (harptab.py, harptab_page.py) | 1,530 | the hardest: notations as data, each reading weighed |
| Pinyin over the words (pinyin.py) | 30, plus pypinyin | pypinyin's algorithm and dictionaries (feature 1) |
| Simplified and Traditional (hanzi.py, with OpenCC) | 70, plus OpenCC | opencc4j (pure Java, Apache-2.0), or OpenCC's own algorithm and text dictionaries for exact output |
| The page itself (page.py: data assembled, scripts inlined by their hashes) | 620 | mechanical |

The phone can start without it. Until it exists, the computer's songs come with the computer's pages (feature 4),
and a song looked up on the phone shows its sheet as plain text.

## Keeping two caracoles in step

Two implementations of the same rules drift apart unless a test holds them together. caracole already does this
between Python and JavaScript: the viewer's theory is checked against the Python theory in Chromium. Do the same for
Kotlin:

- The Python suite writes a **conformance corpus** of inputs (sheets, names, harmonica tabs, search queries, sync
  units) and Python's outputs (page data, identity keys, search results, digests).
- The Kotlin tests read the same files and must match them exactly.
- A change on either side regenerates the corpus or fails it.

Without it, a song could read in one key on the phone and another on the computer, or sync could see one song as two.

## Milestones

Each one ends with something usable.

1. **Foundations.** The Kotlin core, the schema in bundled SQLite (FTS5 checked on a real phone), identity keys,
   canonical JSON and digests, and the conformance corpus. Nothing visible yet, but the corpus passes.
2. **Search with the computer off.** Import the computer's index, add the local server's read routes, and reuse the
   library page. The phone searches every site's index and your songs offline.
3. **Sync from the phone.** The sync engine in Kotlin, the computer's `POST /peer/push` and canonical hashing, the
   Sync page, and the mirror keeping the phone's songs. The 20-songs scenario works both ways, conflicts included.
4. **Lookups.** The politeness core first (client, robots.txt, budgets, pace, cooldowns, cache, job queue, Requests
   tab), then UG, lyrics, LaCuerda, gtptabs.com, harptabs.com, gametabs.net and MuseScore. A new song found and added
   on the phone shows its sheet as text.
5. **The page builder.** Theory, harmony, shapes, harps and winds first; harmonica tabs, pinyin and Traditional
   after. Every sheet on the phone plays as on the computer, including the ones looked up there.
6. **Songbooks, sheet versions, PDFs by printing, alphaTab**, then the rest of the table above as wanted.

Milestones 2 and 3 already cover most of the goal: songs changed on the computer reach the phone and come back.
Milestones 4 and 5 are the bulk of the work.

## Changes on the computer's side

The port needs these in the Python caracole:

- `POST /peer/push`: the computer takes units the phone sends, checked against their digests.
- Version records and lyrics hashed canonicalized, with a sync format bump.
- `GET /api/peer/index`, and the index merged both ways at a sync.
- Cooldowns moved across at a sync (already planned).
- The Sync page, as a tab of the library page.
- The conformance corpus writer, in the test suite.

## Risks and open questions

- **Two implementations to maintain.** Every later change to search, lookups, theory or sync has to be made twice.
  This is the largest cost over time. The corpus catches drift but doesn't prevent the extra work.
- **FTS5 in the bundled SQLite** is unverified. Check `PRAGMA compile_options` on a phone, or fall back to
  sqlite.org's bindings built with FTS5.
- **Page builds on a phone.** The harmony tables are computed for every transposition and mode, so measure how long
  that takes. A page is built once and kept until its sheet or the builder changes, as on the computer.
- **The index's size.** About 400 MB, so the first transfer should be over Wi-Fi.
- **Android's background limits.** The local server lives while the app does. Lookups are short (a few requests),
  but an index import or a long sync belongs in a foreground service or WorkManager.
- **The localhost secret** is a departure from caracole's no-secret rule, and the owner's decision.
- **opencc4j against OpenCC 1.4.1** on real sheets. The corpus will show any difference.
- **Ktor's footprint and start-up time** in an app.

## Alternatives considered

- **Termux, running the Python caracole as is.** It has every feature but auto-chords and YouTube, and
  `android/termux/setup.sh` installs it. But it needs Termux and builds packages on the phone, which is what this
  plan avoids.
- **Android's Linux Terminal** (a Debian VM on some Android 15+ phones). It could run caracole unchanged, but few
  devices have it.
- **Python embedded in the app** (Chaquopy). caracole's jobs start `python -m caracole` as child processes, which an
  embedded Python can't do, and its native packages (rapidfuzz, selectolax, opencc) would need builds for it. Running
  jobs in-process could get around the first problem. This route is far less code than a port and hasn't been tried,
  so it is worth a short spike before committing to Kotlin.
- **An always-on caracole** (the computer, or a small box) reached over a tailnet. No port at all, but nothing works
  without a network.
